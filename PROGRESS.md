| cfabort | ✅ Yes | Compiler + runtime | `<cfabort>` stops template processing with an uncatchable `abort_exception` (never matched by any `catch`, even `catch(any)`); the daemon swallows it and halts the page. **An abort inside a `<cftry>`/script `try` now stays uncatchable** (was BUGS.md "abort inside cftry is re-raised as a catchable Request"): `cf_eh_capture` marks the captured exception `m_isAbort`, and the landing pad's unmatched path re-raises an `abort_exception` via `cf_eh_throw` instead of a catchable `Request`-typed `webstrada::exception` — so `<cfabort>`/`<cflocation>` inside a try abort the request (with the `finally` running first), no catch clause intercepts them, and nested tries don't either. **A bare `abort;` in cfscript** is now a script keyword that calls `cfabort` (previously it resolved as an undefined variable and was catchable); `abort` as a plain variable name (`abort = "hello"`) still works, matching CF. | cfcache | ✅ Yes | Compiler + runtime | Page/fragment caching (`action="cache"`/`"servercache"`/`"optimal"`/`"clientcache"`), `"flush"`, and object-cache `"put"`/`"get"` via the same SQLite-backed store as the Cache* functions. The **body form** (`<cfcache>...</cfcache>`) stores the rendered fragment in the TEMPLATE region keyed by page path + SHA-256 `_pageid:` + `_line:N` (+ optional `_query_` query string and `dependson` values); the `id` attribute does NOT take part in the template key (CF's `generateTemplateKey` never sees it — the cfcache `setId` override only fills `cacheid` for the object cache), so two tags on the same physical line share a key and the second is served from cache. `stripwhitespace` collapses runs of 2+ `\n`/`\r`/`\t` to a single `\r` (CF's `SecurityManager.tokenSeparator`) in the stored *and* displayed fragment (CF re-prints the stripped body); the `metadata` attribute binds the entry's metadata struct (NAME/TIMESPAN/IDLETIME/HITCOUNT/CREATEDTIME/LASTHIT/LASTUPDATED/SIZE) on both hit and miss. The **self-closing form** (whole page, typically at the top of a template) registers a pending store that the request harness finalizes with `cf_cache_store_page` after the page completes (CachingFilter), serializing status/content-type/charset/headers/cookies/body; on a hit the cached page is restored (pre-tag output discarded, CF's `getOut().clear()`), the response headers are replayed, and the rest of the page is skipped (CF's SKIP_PAGE); `action="cache"`/`"optimal"` also add the client headers (`Expires: <GMT http date>` / `Cache-Control: public,max-age=<timespan seconds>` / `Pragma: public`; `timespan` is days→seconds like CF's `setTimespan`, absent → `max-age=-1`) on the miss and store them for the hits. `action="clientcache"` only adds those headers. `action="flush"` removes template-cache entries matching `expireurl` (the `+`/`?`→`_query_`, `*`→`.*` pattern) or all template entries when neither id nor expireurl is given, or object-cache entries by comma-separated `id` (`throwonerror` reports `Could not remove some ids from object cache.`). `action="put"`/`"get"` store/read object-cache values (SerializeJSON blobs) in the OBJECT region; `metadata` works with `get`; a get-miss REMOVES the `name` variable (CF sets it to null, so `isDefined` → NO). `usecache="false"` skips the cache check and headers (the body still renders and a body fragment is still stored, like CF). Attribute validations reproduce CF 2025: **compile-time (uncatchable)** unknown attributes ("Attribute validation error for the Cache tag. The tag does not have an attribute called foo. The valid attribute(s) are useQueryString, action, ..."), bad static action value (which is currently `bogus`/`''`, must be one of `CACHE,CLIENTCACHE,OPTIMAL,FLUSH,SERVERCACHE,GET,PUT`), GET/PUT required attributes (ID,NAME / ID,VALUE), the FLUSH `id`/`expireurl` and `expireurl`/`throwonerror` combination error (with CF's two fixed combos), and empty static `directory`/`dependson`; **runtime-catchable** `Application` errors for a nonexistent directory, bad protocol ("ftp specified for attribute protocol is invalid." / "Valid values are HTTP:// or HTTPS://"), `key`+`region` together, `metadata` without an end tag, a self-closing tag inside an included template ("CFCache must have an end tag if used inside an included template."), empty `id`, invalid `dependson`, and `flush` with both `id` and `expireurl` ("ID and EXPIREURL cannot be specified together for action FLUSH."); dynamic GET/PUT missing attributes throw a catchable `Template` "Attribute validation error for cfcache." The `directory` attribute is validated (empty/non-existent) like CF but storage stays in the engine's SQLite cache (a documented divergence). **Byte-verified against CF 2025** (2026-08-09, after the `caching` package was installed on the RDS host) in tests/cfm/cfcache_test.cfm (clientcache + catchable validations) and tests/cfm/tier2_cfcache_test.cfm (object put/get/flush, metadata, fragment hits, stripwhitespace, dependsOn, get-miss leaving the variable undefined); the whole-page miss/hit needs two requests so it is pinned by the `CfcacheTagTest` unit tests. The metadata `HITCOUNT` now matches CF: a `put` resets it to 0 and each `get` increments it, so a fresh get reports `OBJECT:1` every request (previously the counter was never reset on overwrite and accumulated across requests in the SQLite store; fixed in `CacheStore::put`'s upsert). |

| cfcatch | ✅ Yes | Script form: `catch (type var) { }` clauses dispatch by type via the CF exception-class model: `cf_eh_best_match` (src/core/core_eh.cpp) implements `findThrowableTarget`/`findCustomTarget` exactly like CF 2025. **Built-in runtime errors match by the closest class ancestor across ALL clauses** (order-independent; ties by clause order): catch types resolve to CF classes (`expression`→`RuntimeException`, `application`→`ApplicationException`, `database`→`DatabaseException`, `template`→`TemplateException`, `missinginclude`→`MissingIncludeException`, `security`→`AccessControlException`, `object`→`ObjectException`, `searchengine`→`SearchEngineException`, `any`→`Exception`), so `catch(expression)` catches every built-in runtime error (division by zero, undefined var, ... all `RuntimeException`s), a real `1/0` (ExpressionException) is NOT caught by `catch(application)`, and a missing `<cfinclude>` (MissingIncludeException) matches `catch(missinginclude)`/`catch(template)`/`catch(expression)`/`catch(any)`. **Custom `throw`/`<cfthrow>` types match by exact name over `any`** (a later `catch(myType)` beats an earlier `catch(any)`, dotted-prefix partial matches work: `throw(type="my.custom.type")` → `catch(my.custom)`/`catch(my)`), and never match `catch(expression)`/`catch(application)` — CF's `findCustomTarget`. **Reserved built-in type names in `throw`/`<cfthrow>`** (`database`, `template`, `security`, `object`, `missinginclude`, `expression`, `lock`) are replaced by an ApplicationException reporting type `Application` with "Attribute validation error for tag CFTHROW." / "... function throw." (CF 2025's `ThrowTag.validate`), so `throw(type="database")` does NOT match `catch(database)`. User-thrown custom exceptions carry a custom-ness flag (`webstrada::exception::m_isCustom`, persisted through capture→rethrow via `cfvariant::m_isCustomException`) so `<cfrethrow>` keeps exact-name matching. `cfabort` never catches; `cfcatch` binds the caught struct (TYPE/MESSAGE/DETAIL/ERRORCODE/EXTENDEDINFO/TAGCONTEXT) and may be chained. **TAGCONTEXT is populated by the call-stack (stacktrace) feature**: the JIT pushes a `{template pathname, line}` frame at every template / UDF / component-method / component-construction entry, updates the top line before each statement and pops on every exit (normal and unwinding); the first landing pad an unwinding exception reaches snapshots the live stack into the in-flight exception (`m_stackTrace`), so `cfcatch.tagContext` is an array of `{TEMPLATE, LINE}` structs with element [1] = where the error occurred, matching CF (byte-verified: tests/cfm/stacktrace_*_test.cfm, `StackTraceTest` unit tests). A `rethrow`/the unmatched `cftry` path re-raise a fresh exception carrying the original tagContext (cf_eh_throw rebuilds `m_stackTrace` from the captured TAGCONTEXT), like CF rethrowing the same Java exception. Tag form: `<cfcatch type="t" var="name">` inside `<cftry>`; `<cfcatch>` outside a `<cftry>` is rejected at compile time. Verified byte-for-byte against CF 2025 in tests/cfm/cftry_tag_test.cfm + cfcatch_class_matching_test.cfm + `JitExpressionTest.Catch*/CustomThrow*/ReservedType*`/`CfincludeTest.MissingIncludeMatchesMissingIncludeHierarchy` unit tests (was BUGS.md "cfcatch type matching is exact-name only"). |

| cfcomponent | ✅ Yes | Compiler + runtime. `.cfc` files compile into a component definition (ComponentInfo): the top-level `<cfcomponent>` body becomes a construction function that runs at instantiation (setting `this.`/`variables.` members), `<cffunction>` blocks become JIT-compiled methods (`component_method_entry_fn`, direct calls with the instance's `variables`/`this` scopes), `<cfproperty>` declarations feed SerializeJSON and `GetComponentMetaData`. Components are first-class values (`cfvariant::Component`): `this` scope (public members, keys uppercased like CF) doubles as the struct surface (IsStruct/StructKeyList/SerializeJSON/`o.x` work on it), `variables` scope holds private instance variables, unqualified reads resolve local → variables → this (never the caller's page), unqualified writes go to `localScope` for declared local names (`var`) and to the component `variables` scope otherwise, and methods are invoked by direct JIT entry with CF access control (private methods are not callable externally; `StructKeyExists`/StructKeyList hide them). During method execution, `rt->currentPath` is set to the component's file path so relative component/include paths resolve against the component directory. Component dot-paths (`createObject("component", "a.b.c")`, `new a.b.c()`, `extends`, `implements`) resolve relative to the current template/component directory first and fall back to the web root (`rt->webRoot`), matching ColdFusion; dot paths with directories or filenames containing literal dots (e.g. `MangoBlog_1.4.3`) use backtracking on-disk resolution to resolve correctly. Function argument and return types with custom component names (e.g. `returntype="Setup"`) validate against the component/interface hierarchy via `IsInstanceOf`. **`this.mappings` in `Application.cfc`** is supported: custom directory mappings set in `Application.cfc`'s pseudo-constructor (e.g. `this.mappings["/org/mangoblog"] = ...`) are registered on the application context and used to resolve dot/path component references (`createObject("component", ...)`, `new ...`, `extends="..."`, `implements="..."`) and `<cfinclude template="...">` paths. **`super.`** explicitly dispatches methods to parent implementations across multi-level inheritance chains (`super.method()`). **Script-form components** (`component { ... }` at the top of a `.cfc`) are supported: the textparser grammar's `overrideStartTokens` parses a `.cfc` that starts with `component`/`import`/`interface`/`final`/`abstract` or a `//`/`/*` comment as a top-level `ScriptExpression`, and `compileComponent` detects that form, parses the component attributes (`extends=".."`, etc.), collects `property name=".." type=".." ...;` declarations, script methods (with `public`/`private`/`package`/`remote`/`final` access modifiers, return types either before the name or as `returntype=".."`, default params) and compiles the remaining body statements as the construction body. | cfcontent | ✅ Yes | Compiler + runtime. Sets the response MIME type and output character encoding from the `type` attribute (`text/html; charset=ISO-8859-1`), discards prior output by default (`reset`, default `yes`) or preserves it (`reset="no"`), and can replace the page output with a file's (`file`, optional `deletefile`) or variable's (`variable`) contents (binary passthrough; all other page output is ignored). | cfexecute | ✅ Yes | Compiler + runtime (tag_execute.cpp). Runs the `name` executable with the (Unix-tokenized) `arguments` and captures stdout to the page, the `variable` attribute or the `outputfile`, and stderr to `errorVariable`/`errorFile`. Faithfully mirrors CF 2025's ExecuteTag + ProcessExecutor: string arguments are tokenized with `getProcessCommand`'s rules (space-separated, double-quoted segments kept as one argument, a quote mid-argument is literal; array arguments map element-per-arg), relative output/error file paths resolve against the CFML temporary directory (GetTempDirectory), and the `timeout` (seconds) limits how long CF waits for the process output — with **no timeout CF does not wait at all** (ProcessExecutor's non-blocking race: `blocking` is false and `timeout` is 0, so neither `waitFor` nor the `join` runs and the output is read immediately — on CF 2025 the `variable` stays undefined and the page gets nothing; this engine reproduces the race and leaves the variable unbound). With a timeout the tag waits for both output streams to hit EOF (the process to exit) and captures the output; a deadline miss throws CF's catchable `Application` "The requested action did not complete in a timely manner. ## Compiler internals: exception-safe codegen state

The codegen save/restore of every compile-time `thread_local` state slot
(`g_ehContext`, `g_currentCatchExn`, `g_currentFuncCleanupBB`,
`g_returnCtx`, `g_compileInFunctionBody`, `g_currentOut`,
`g_insideCfoutput`) is now exception-safe via `ScopedCodegenState<T>`
(src/codegen/codegen_internal.h). A compile-time abort (an unimplemented tag,
a parser/expression error) unwinds the compile function without running the
manual restore, so previously the slot was left pointing at dead state and the
NEXT component compile read a garbage landingPadBB and segfaulted in LLVM IR
construction (`llvm::Use::set`). Minimal repro: a component whose method body
throws at compile time (e.g. the unimplemented `<cflock>` tag inside a
`<cftry>`) followed by a normal component — the second compile crashed before
the fix (observed in MangoBlog setup: SubscriptionHandler's `setup()` aborts on
a `<cfschedule>` compile abort, then Links/Handler.cfc's compile segfaulted). Now the aborted
compile leaves no residue and the next compile runs normally — verified by
`ComponentTest.AbortedComponentCompileDoesNotPoisonNextCompile`.

## Abstract database layer

The CFML query runtimes (`<cfquery>`, `queryExecute()`, `<cftransaction>` and the
`transaction*()` built-ins) execute SQL through an **abstract database layer**
(`include/webstrada/db.h`, `src/db/db.cpp`): `cfml::cf_run_query` and the
transaction helpers only ever see the `webstrada::db::DBConnection` /
`DBResult` / `DBDriver` interfaces, and the concrete backend is selected per
datasource by the driver registry (`registerDriver` / `openConnection`, which
lazily registers the built-in backends).

**Backends:**

* **SQLite** (`src/db/db_sqlite.cpp`, `SqliteDriver` + `SqliteConnection`): each
  datasource is the per-DSN `DNS_<name>.sqlite` file (WAL mode + busy timeout);
  the `sqlite3_prepare_v2` multi-statement tail loop, `sqlite3_column_*` cell
  conversions, the CF recordcount semantics (DDL → 1, DML → affected rows) and
  generated-key capture. This is the default backend for a datasource with no
  config entry (the pre-config behavior). MangoBlog's setup wizard
  (`admin/setup/setup.cfm`) now offers **SQLite** as a database type: choosing it
  runs `setupDatabase()`'s `<cfinclude template="sqlite.sql">` (a SQLite port of
  `mysql.sql` — backtick/charset clauses dropped, `KEY`/`UNIQUE KEY` → `CREATE
  INDEX`/`CREATE UNIQUE INDEX`, `int(10) unsigned` → `integer`, multi-row
  `INSERT`s kept), creating the 19-table blog schema as a `DNS_<name>.sqlite`
  file when the datasource is configured with the SQLite backend. MangoBlog's
  `PostsGateway` date queries are also ported: the MySQL/MSSQL
  `YEAR()`/`MONTH()`/`DAY()` calls became SQLite `CAST(strftime('%Y'|'%m'|'%d',
  posted_on) AS INTEGER)` (all 27 usages in getByDate/getCountByDate/
  getActiveYears/getActiveMonths/getActiveDays), so the calendar
  `getActiveYears`/`getActiveMonths`/`getActiveDays` archives run on SQLite —
  the CAST is required because SQLite never equates TEXT ("2026", zero-padded
  "08") with the integer parameters; `getByDate`/`getCountByDate` and the blog
  listing (`getAll`/`getByIds`) are still blocked on SQLite by a pre-existing
  malformed `ON ... ON` join chain and a query-column `returntype` issue (see
  BUGS.md). Guarded by `CfincludeTest.MangoBlogSqliteSetupSchemaRuns` /
  `MangoBlogSqliteStrftimeCastDateQueries`.
* **MySQL/MariaDB** (`src/db/db_mysql.cpp`, `MySqlDriver` + `MySqlConnection`,
  via the MariaDB Connector/C client library `libmariadb`): a datasource
  configured with `backend="mysql"` connects to the server described by its
  host/port/database/username/password fields. `execute()` runs the whole SQL
  script through `mysql_real_query` with `CLIENT_MULTI_STATEMENTS` and surfaces
  only the FIRST result; cells are converted from MySQL field types (int →
  Number/Long, float/decimal → Float, text/char/varchar and text-charset blobs
  → String, binary blobs → Binary), non-result statements report
  affected-rows / the auto-increment `GENERATEDKEY` (via `mysql_insert_id`),
  and transactions use BEGIN/COMMIT/ROLLBACK + SAVEPOINT / ROLLBACK TO.
  `<cfinsert>`/`<cfupdate>` read the table's columns through
  `SHOW FULL COLUMNS` (Key="PRI" marks the primary key).
* **PostgreSQL** (`src/db/db_pgsql.cpp`, `PostgresDriver` + `PostgresConnection`,
  via the libpq client library; `backend="postgres"` with `"postgresql"`/`"pg"`
  aliases): a datasource configured that way connects to the server described
  by its host/port/database/username/password fields (connection string built
  from the config; `connect_timeout` from the query timeout). `execute()` runs
  the whole SQL script through `PQsendQuery`/`PQgetResult` (the simple query
  protocol executes a multi-statement string statement by statement) and
  surfaces only the FIRST result; cells are converted from PostgreSQL column
  OIDs (bool → **Number 1/0 like CF's PG driver** (verified on CF 2025: a PG
  boolean column renders `1`/`0` and its cell class is `java.lang.Integer`,
  not `true`/`false` — the byte-compare of `postgres_test.cfm` forced this
  fix), int2/int4/int8/oid → Number/Long with the int32 bound, float4/float8/numeric
  → Float, bytea → Binary decoding both the `\x` hex and legacy octal escape
  forms, date/time/timestamp/interval and everything else → the server's text
  representation), non-result statements report affected rows (`PQcmdTuples`,
  DDL → 1) with no implicit-OID generated key (modern PostgreSQL, matching
  pgjdbc's `getGeneratedKeys` without `RETURNING`; an `INSERT ... RETURNING`
  statement is a result set and surfaces its columns), and transactions use
  BEGIN/COMMIT/ROLLBACK + SAVEPOINT / ROLLBACK TO SAVEPOINT. `<cfinsert>`/
  `<cfupdate>` read the table's columns from `information_schema` (joined with
  the PRIMARY KEY constraint in the connection's `current_schema()`).

A datasource is selected per DSN name by `webstrada::config::datasources` — a
case-insensitive map (`CiStrLess`, mirroring ColdFusion's case-insensitive
datasource names) that preserves the casing of the name as first entered, so
`appdb` / `AppDb` / `APPDB` all resolve to the same datasource and the admin
panel shows the name as typed. Connection params come from the config
entry. The daemon now loads them from the server configuration file
(`webstrada-config.json`, see "Server configuration file" below); the CLI and
unit tests additionally support the `WSDATASOURCE_<UPPER_DSN>_*` environment
variables at startup (`config::loadDatasourcesFromEnv`, see config.h). A
datasource with no config entry is treated as SQLite.
`db::datasourceConfig(dsn)` exposes the resolved parameters (backend +
server fields) to the metadata layer so `<cfdbinfo>` dispatches its
backend-specific introspection without reopening the connection.

`DBResult` carries the columns (name/type/values), `rowCount`, `generatedKey`
and `hasGeneratedKey`; `cf_run_query` maps it to the `cfvariant` Query object
and the `result` struct. `DBStoredProcResult` (added for `<cfstoredproc>`) carries
`resultsets`, the `statusCode` and the `outValues`; `DBConnection::storedProc()`
executes a `CALL` on MySQL/PostgreSQL (the base implementation throws for
backends without stored procedures, e.g. SQLite). 

**Diagnostics:** `openConnection` wraps every backend connection in a
`LoggingConnection` (src/db/db.cpp) that dumps **every operation on the
abstract DB layer** to stdout when `webstrada::config::enableQueryLogging` is on
(the same flag that gates the `[cfquery]`/`[cfstoredproc]` lines in the CFML
layer, and exposed as the admin "Query Logging" setting): `[db] <backend> open
dsn=..`, `[db] <backend> execute dsn=.. maxrows=..` + the SQL, `begin`/
`commit`/`rollback`, `savepoint <name>`/`rollbackTo <name>`, `tableColumns
<table>`, `storedProc proc=.. params=..`, and `close` — logged *before* the call
delegates, so even a statement that then fails is visible. When an operation
**fails**, the wrapper additionally prints an `[db] <backend> ERROR dsn=..` block
(`op`, `message`, `detail`) before rethrowing the original exception unchanged,
so a request's DB errors show up in the terminal next to the statement that
caused them (the dev web server http-dev.py tees the daemon's stdout to the
console). All backends throw a `"Database"`-type `webstrada::exception`
("Error Executing Database Query." + the driver detail), which the JIT maps to a
catchable CFML `database` exception — `catch(type="database")` matches and
`cfcatch.type` is `"Database"`. The wrapper owns the
inner connection and works for every backend uniformly; the CLI and unit-test
binary keep the flag off because their stdout is a data channel. Covered by the
`CfQueryTest.DbLayerDumpsOperationsToStdout` and
`CfQueryTest.DbErrorLoggedToStdoutAndThrowsDatabase` unit tests.

## Server configuration file + `__` compiler extensions

The server configuration now lives in a JSON file (`webstrada-config.json`).
The daemon resolves it at startup — `WEBSTRADA_CONFIG` env overrides, else next
to the WebStrada binary (`src/config.cpp`), the same rule as the SQLite
scope/cache databases — loads it into the `config::*` globals, and **bootstraps
it from the built-in defaults** when it does not exist yet (so the file always
reflects the effective configuration). `config::save()` persists the globals
atomically (temp file + rename). Prefork workers re-read it per request via
`config::reloadIfChanged()` (a single `stat()` when unchanged), so an admin
update written by one worker becomes effective on the next request in every
worker without a restart. `enableWhitespaceManagement` stays compile-time
(affects newly compiled templates only). Wired in `appserver::init` (before the
fork) + `worker::process_request`.

**Compiler-extension functions** (`__` prefix, reserved like C's `__`
identifiers): engine-provided functions callable from CFML, compiled as direct
JIT calls (`cf___<name>(args, argc)`, uniform ABI), never runtime-dispatched
and never shadowable by a UDF/variable. The codegen's generic fallback
(`codegen_expr.cpp`) emits the direct call and rejects unregistered `__name`
calls at compile time; the `#...#` interpreter (`core_interp.cpp`) dispatches
through the same registry (`src/cffunctions/fn_extensions.cpp`) and raises a
catchable runtime error for unregistered names. Registered:

* `__configGet()` — struct of the effective config (`{settings, datasources}`)
  straight from the globals; datasource passwords masked as `****`.
* `__configSet({settings?, datasources?})` — merge-updates the globals and
  persists via `config::save()`. Unknown setting keys / non-numeric numerics /
  unsupported backends / named arguments are rejected with clear errors; a
  password of `****` keeps the existing secret; `{action: "delete"}` removes a
  datasource.
* `__configReset()` — resets every config global to the built-in defaults and
  persists (the panel's "Restore Defaults").
* `__datasourceTest(name)` — real connection attempt through the DB layer →
  `{verified, error}`.
* `__serverInfo(excludeAdmin)` — dashboard runtime stats `{state, version,
  uptimeSeconds, requestsServed, avgResponseMs, recentRequests}` tracked per
  worker process by `webstrada::stats` (`src/server_stats.cpp`;
  `worker::process_request` records request begin/end with the response
  status). An optional truthy `excludeAdmin` argument drops recent requests
  whose template path starts with `/admin` — the dashboard's "Hide admin
  requests" switch passes it via `?excludeAdmin=true` so the filtering happens
  server-side.
